## Context

J-Link MCP V2 是一次不兼容旧版的重新实现。仓库目前没有 Rust 生产代码，因此可以先固定状态所有权、依赖方向和可行性门禁，再开始实现。首版只面向 Windows x64、本机 stdio、SEGGER J-Link、ARM Cortex-M、SWD/JTAG；HSS 行为以旧版实现为首要行为基线，并用候选 `JLink_x64.dll`、真机和必要的社区 SDK 镜像补齐最小 ABI 证据。

项目的主要风险不在 MCP 路由本身。旧版已经证明长时 HSS 采集期间交错控制写入这一场景成立；V2 仍需验证的是候选 DLL 的 HSS ABI/帧格式兼容性、既定上限下的调度与存储性能、主进程退出后的采集续行、复合 DWARF 数据定位以及目标 Windows Codex 对结构化结果和资源的实际支持。生产实现必须在这些 V2 实现假设得到证据前保持可撤销。

## Goals / Non-Goals

**Goals**

- 让每份可变运行状态只有一个写入所有者，并通过单向依赖和消息传递协作。
- 让地址、类型、边界、状态转换、错误和数据质量等业务规则只实现一次。
- 以两个进程和少量职责明确的 crate 隔离 MCP、J-Link DLL 与采集存储故障。
- 在正式纵向实现前，用最少但足够的 Phase 0 实验验证会推翻方案的高风险假设。
- 让每项 Requirement 能追踪到一个主要测试和一份证据，同时复用未失效的昂贵硬件/客户端证据。
- 保持公共工具和普通返回简洁，把完整 HSS 数据放在不可变资源中按需读取。
- 缓存由内容身份决定的符号解析结果，并只合并语义安全的目标内存访问，减少重复解析和 DLL 往返。

**Non-Goals**

- 公开发布、多人权限管理或商业交付；V1 仅供内部个人使用。
- 兼容旧版工具、配置或采集格式。
- 支持 RTT、SVD、断点、任意 GDB/J-Link 命令、服务端绘图、CSV 或历史数据库。
- 验证或声明支持 ChatGPT Desktop、Claude 及其他非 Windows Codex 客户端。
- 把整个 J-Link SDK、GUI 或常驻系统服务引入首版。
- 假设同一 J-Link 连接允许并发进入 DLL。
- 在 MCP 内实现写入授权、二次确认或用户权限体系。

## Decisions

### 1. 使用两个进程、四个 workspace crate

首版 workspace 使用以下边界；目录名称可以在初始化时机械调整，但职责和依赖方向不得改变：

| Crate | 类型 | 唯一职责 | 允许依赖 |
|---|---|---|---|
| `jlink-mcp` | binary | stdio 传输、六工具 Schema、请求编排、配置文件所有权、Worker 连接、已完成采集查询与资源暴露 | `jlink-domain`、`jlink-capture` |
| `jlink-worker` | binary | 探针租约、会话状态机、唯一 DLL gateway、HSS 生命周期、活动采集写入和恢复 | `jlink-domain`、`jlink-capture` |
| `jlink-domain` | library | 公共/IPC 值对象、错误、状态转换、固件与 DWARF 访问计划、纯业务校验 | 仅通用第三方库，不依赖另外三个 crate |
| `jlink-capture` | library | 采集格式、原子存储、不可变快照、分页和四种查询算法 | `jlink-domain` |

依赖只能沿表中方向流动，不允许循环。`jlink-mcp` 不加载 DLL，`jlink-worker` 不解析 MCP 请求或写配置，`jlink-capture` 不访问探针。若后续某模块尚不足以成为独立 crate，先作为上述 crate 的私有 module，而不是建立新公共层。

选择此方案而非“每个功能一个 crate”，是为了保留进程级故障隔离和核心依赖边界，同时避免首版产生大量只转发调用的包。

生产 workspace 的物理结构固定为根 `Cargo.toml` 加 `crates/jlink-domain`、`crates/jlink-capture`、`crates/jlink-worker`、`crates/jlink-mcp`。质量与依赖检查只放在根配置或 `scripts/`；不得为构建辅助、测试夹具或共享工具建立第五个 crate。内部 module、类型和函数默认私有，只有确实跨 crate 的稳定值对象或行为才公开。

禁止创建没有独立领域责任的 `utils`、`common`、`manager`、`service` 或 `repository` 层，也禁止只转发参数和返回值的 helper。新增 helper、依赖、持久状态或抽象必须具有独立语义、必要复用价值或能实质降低正确性复杂度；不得仅为缩短函数或预想未来扩展而增加概念。目标 IAR 工程中的测试 C/header 修改遵守该工程规则优先，并应用 embedded-code-style 的命名、英文相邻文档和结构极简约束。

当前 2.1–5.5 实施批次只以 S32K144、SWD 4000 kHz 和 J-Link 6.98a 形成硬件证据。JTAG 的公共枚举与非硬件合同保留，但在完成单独真机证据前不得声明受支持，也不得在 JTAG 失败时静默回退为 SWD。任务 5.6 和 5.7 不属于该批次，不得提前勾选、归档 change 或声明发布完成。

### 2. 可变状态采用单一所有者

| 状态 | 唯一写入所有者 | 其他组件访问方式 |
|---|---|---|
| 工程/用户配置与有效配置缓存 | `jlink-mcp` | Worker 只接收带指纹的不可变配置快照 |
| ELF/DWARF 索引与 `AccessPlan` 缓存 | `jlink-mcp` | 其他组件只接收绑定 ELF 身份和解析器版本的不可变计划 |
| 探针租约、DLL 句柄、连接、目标状态、验证缓存 | `jlink-worker` 的会话状态机 | MCP 通过 IPC 命令和只读状态快照访问 |
| 活动 HSS 状态、截止时间、排空位置、活动文件 | 执行该采集的 `jlink-worker` | MCP 按采集 ID/键查询 Worker 状态 |
| 已完成采集文件 | 发布后不可变 | MCP 和查询代码只读；删除不是 V1 公共能力 |
| 查询游标快照 | `jlink-mcp` 的查询会话 | `jlink-capture` 以纯函数读取绑定快照 |

同一业务状态不得在两个组件中各自维护“权威副本”。IPC 返回的是观察快照；失联后必须重新发现事实，不能用主进程缓存反推 Worker 状态。

### 3. 相同业务规则只实现一次

纯规则放在 `jlink-domain` 或 `jlink-capture` 的唯一函数中，MCP Schema 只做形状校验，Worker 只执行已验证计划：

- 地址加长度、Flash/RAM/MMIO 区间和对齐：统一的范围校验器。
- DWARF 路径、成员偏移、数组展开、位域与 TypedValue：统一生成不可变 `AccessPlan`，普通读写和 HSS 共用。
- HSS 生命周期和完整性：两个独立状态机，不在路由、存储和 Worker 中重复判断。
- 错误码到公共错误结构：单一映射表；底层错误不得在多个工具中重复翻译。
- 阈值、变化、时间关系和分页排序：只由 `jlink-capture` 查询引擎实现，`around_event` 复用 `window` 边界而不复制原始样本逻辑。

函数保持单一目的：公开函数表达一个领域动作；只有私有纯函数具有独立语义、必要复用价值或能实质降低复杂度时才拆分，不能只为缩短函数增加 helper。公共包装函数不得只因不同调用方而复制同样逻辑。每个公开函数和所有包含非显然安全前提的内部函数必须写英文 Rust 文档注释，说明输入、输出、错误、状态副作用和不变量；不把嵌入式 C 的命名与文件布局规则机械套用于 Rust。

### 4. Worker 通过版本化本地 IPC 协作

Windows 命名管道承载带长度前缀的版本化 JSON 控制消息。高频样本不经 IPC 回传，Worker 直接写 Capture Store；IPC 只传命令、状态、元数据和文件身份。每个请求包含协议版本、请求 ID 和幂等边界，响应区分成功、确定失败与 `EXECUTION_UNCERTAIN`。

Worker 使用探针身份派生的跨进程租约和可发现端点。MCP 启动时先尝试附着已有 Worker，再决定是否创建，并把自身 PID 作为内部启动参数交给新 Worker；Worker 持有只读同步句柄检测该父进程是否退出。有活动 HSS 的 Worker 在父进程退出后续行到固定截止时间，完成 Stop、尾排空和原子落盘后退出；没有活动 HSS 时，孤立 Worker 退出并释放租约。新 MCP 优先重新附着尚存 Worker；若完成边界恰逢旧 Worker 退出，只允许对只读状态执行一次事实恢复并从持久化索引重新查询，不重发 HSS Start。

选择命名管道而非进程标准输入，是为了让 Worker 在 MCP 主进程退出后仍可存活并被新进程发现；选择 JSON 控制消息而非把采样流放进协议，是为了可诊断且不让 IPC 成为 1 kHz 采集瓶颈。

### 5. 所有 DLL 调用经过一个串行 gateway

`jlink-worker` 内只有 gateway 能持有解析后的函数指针并进入 DLL。普通命令和 HSS 排空请求进入同一调度队列；HSS 活动时调度器优先排空，只在一次排空完成后的受控间隙执行允许的变量或 RAM/MMIO 写入，然后立即恢复排空。任何时候都不会从两个线程同时进入同一连接的 DLL。

这保留了未来在有可靠证据后增加并行会话的空间，但 V1 不以未经证实的 DLL 并发安全为前提。

gateway 的每个动态函数指针必须逐项匹配冻结 J-Link 6.98a SDK 的参数、返回类型和 Windows x64 调用约定，不得把 P0 实验中的简化声明直接当作生产 ABI。特别是指针错误结果、`char` 状态结果和 `int` 执行结果必须按各自原始类型解释，不能用统一的 `i32` 或 `void` 声明吞掉返回事实。冻结 6.98a 的通用 `JLINKARM_ReadMem` 在内部完整传输请求字节后返回状态 `0`，非零表示失败；`JLINKARM_ReadMemU32` 等类型化读取则返回完成项目数，两类返回语义不得混用。打开 DLL 会话时使用支持日志与错误回调的入口，把单次会话诊断收集到有界本地缓冲；该诊断只用于失败根因和验证证据，不进入普通 MCP 成功结果，回调不得重入 DLL 或拥有业务状态。

HSS 动态 ABI 只加载 F0-A 冻结的 `JLINK_HSS_GetCaps/Start/Read/Stop`，并把四个导出视为一个可选能力组：任一缺失都必须列出实际缺项，普通调试能力仍可使用，HSS 启动则返回 `DLL_EXPORT_MISSING`，不得寻找替代导出或回退路径。Windows x64 下 `HssBlock` 固定为四个连续 little-endian `u32`（16 字节），`HssCaps` 固定为 `max_blocks/max_frequency_hz/flags/reserved[5]`（32 字节）；`Start` 的主线 6.98a 标志固定为 `0`，实验性微秒时间戳标志 `1` 不进入 V1。原始帧按一个 little-endian `u32` 源时间戳加声明顺序的块载荷解析，批次尾部不足一个完整帧的字节必须保留给后续质量判定，不能静默截断。

HSS 启动先在 `jlink-mcp` 中生成无副作用的不可变 `HssStartPlan`：每个顶层选择项必须由当前 ELF/DWARF 生成一个固定连续的 `AccessPlan`，复合成员映射保留在计划内，但 Worker 只接收已经展开并绑定固件身份的块。V1 固定最多 10 个块、40 字节样本载荷和 44 字节原始记录，持续时间为 1–300 秒，目标频率为 1–1000 Hz；冻结 6.98a 能力必须报告 `flags=2`、保留字段全零、毫秒源时间戳 1000 Hz/1000 us 且单调，不能据此宣称微秒分辨率。规范化请求指纹不包含 `capture_key`，但必须包含按唯一规则 ID 确定排序的完整启动规则，使规则顺序变化保持等价、规则内容变化产生冲突；规则匹配仍由后续唯一查询实现负责，启动计划不得静默丢弃规则。Worker 以探针身份、完整 `TargetConnectionSpec` 指纹、键和请求指纹共同确定采集 ID；请求指纹继续包含固件身份与访问计划。只有目标连接身份和规范化请求都等价时才返回既有身份，任一变化均返回 `CAPTURE_KEY_CONFLICT`。启动预检复用 SES-003 的唯一恢复流程并保留全部恢复通知，不实现第二套 halt/HardFault 规则。4.2 只冻结计划和预检；公共 `jlink_hss start` 只有在 4.3 的持续排空、内部 Stop 和尾排空调度可用后才能接入，不能在尚无调度器时返回伪成功。

4.3 的 Worker 管道监听线程只负责接受帧、记录入队时刻和等待响应，不持有 DLL 或目标状态；主调度线程继续唯一拥有 `DllGateway`、会话和 HSS 状态。活动采集期间主线程至多等待 1 ms，且每次分派前先排空 HSS；仅变量及 RAM/MMIO 写入可在该排空后串行执行，并记录请求、开始、完成、结果、写前样本数和紧随其后的排空样本数，失败写入仍返回原错误但不终止可继续的采集。达到固定截止时间后调度器只调用一次内部 Stop，再以 1 ms 间隔排空，直到连续 20 次空读取；500 ms 内未收敛、尾部仍非完整帧或排空失败均不得报告正常完成。生产读取保留 F0-A 冻结的 6.98a 语义：`JLINK_HSS_Read` 返回正数时按字节数保留，返回 0 但哨兵帧发生变化时按一个完整记录接收；所有不完整尾字节跨调用保留，不静默截断。4.5 已将原始字节从 Worker 全量内存保留替换为同线程追加 Capture Store；内存只保留跨调用不完整尾字节、状态和质量证据。

4.4 使用唯一纯状态机分别持有生命周期和数据完整性：正常路径仅允许 `starting -> running -> stopping -> completed`，终态不可重写；`completed` 可以独立携带 `complete/degraded/unknown`，不得用数据降级替代流程终态。当前任务只在存在不完整尾字节时确定标记 `degraded`，其余正常完成保持 `unknown`，直到 4.6 的频率、间隔、溢出和丢样质量证据能够支持更强结论。DLL Start 明确失败会保留同一采集 ID 的 `failed` 事实并继续返回可重试的 `HSS_START_FAILED`；同键等价请求随后只恢复该失败身份，不重复 Start。活动采集的读取或尾排空失败只有在内部 Stop 已确认后才能受控收口为 `failed`，并保留完整记录、尾字节、失败码和恢复通知；若 Stop 本身无法确认，则不得伪装为受控 `failed`，Worker 按硬件停机规则退出，后续只能由 4.5 的临时文件扫描标记为 `aborted + unknown`。`aborted` 仅用于进程中断、存储中断或启动恢复事实，不引入公共 stop/cancel。

4.6 在每次排空后以冻结记录步长解析 32-bit little-endian 源时间戳，并按 `timestamp_ms × 1000` 生成整数 `timestamp_us`；持久化质量同时保留 `source_unit=milliseconds`、1000 Hz、1000 us 源分辨率、Worker 自 Start 返回后的单调微秒时间域，以及“Start 调用窗口 + 1 ms 源分辨率”的映射误差上界。请求频率与实际样本数分开保存，实际频率用源首尾时间戳推导的 milli-hertz 固定点表示；间隔保存 count/min/max/total、碰撞、gap 和回退计数。短读取与非记录边界读取只生成有证据等级的质量事件，字节仍跨调用保留；最终短尾、无法由时间戳碰撞抵消的 gap、时间回退或确认溢出会把完整性降为 `degraded`，但稳定降频本身不把 `completed` 改成工具失败。冻结 6.98a 没有独立 overflow/sequence counter，因此无直接信号时 `loss` 与 `overflow` 必须为 `unknown` 且省略数值，不能输出零；只有可识别的直接溢出信号才形成 `confirmed` 事件和受影响记录范围。质量事件按类别与证据等级聚合首尾 Worker 时间和记录范围，避免长时采集产生无界终态元数据。

具体器件命令必须在同一 DLL 会话内得到确定接受后才能建立活动目标身份。gateway 必须同时检查命令返回码及冻结 API 定义的错误输出，不能在 `device = ...` 被拒绝后仅凭通用 Cortex-M 连接或静态器件数据库查询继续。进入 `BeginDownload` 前，活动 gateway 必须已经保存经确认的具体器件选择；否则在首个 Flash 副作用前失败。3.7 真机诊断先通过冻结 J-Link 6.98a SDK 修正 ABI、器件命令错误观测和有界日志，再确认单独 `halt` 无法使目标进入 Flash RAMCode 所需状态；目标 IAR 工程的 `--jlink_reset_strategy=0,0` 与 IAR Cortex-M Normal(0) 下载流程证据则表明下载前应执行复位并暂停。因此 flash、整片 erase 和范围 erase 在所有输入及 Flash 边界校验通过后，必须通过唯一 gateway 执行一次 `reset_halt` 并确认 `halted`，再进入 `BeginDownload` 或 `JLINK_EraseChip`。准备失败必须在首个 Flash 修改调用前返回 `TARGET_RECOVERY_FAILED`；不得降速、重试、调用 Commander 或增加其他 fallback。`EndDownload` 成功只证明下载事务完成，不能作为目标仍处于可读状态的证据；flash 请求启用默认校验时，必须再次执行一次 `reset_halt` 并确认 `halted`，随后完成读回校验，最后才应用请求的 `after`。该下载后准备只属于 flash 内部默认校验；独立 `verify` 保持只读，不增加隐式复位、暂停、恢复运行或新的公共字段。

器件专用 J-Link 首次建连初始化可能复位或暂停内核，从而清除连接前的 HardFault。Worker 只对建立目标会话后的首个可观察状态及同一活动会话内的后续状态负责，不得根据连接前测试夹具状态伪造恢复通知。T-P1-SES 的 HardFault 真机证据必须在同一 Worker/DLL 会话内注入真实内核异常，再调用生产恢复状态机；注入入口只在测试编译中存在，不进入生产二进制、IPC 或 MCP 合同，不修改 Flash 或冻结 OUT。

断开状态的显式 validate 无法根据器件初始化后的状态可靠恢复建连前的运行意图，因此必须要求 `after: run | halt`。临时会话先复用 SES-003 的唯一恢复流程，再显式收口到请求状态，并报告最终状态和恢复通知；不得建立第二套恢复规则。活动连接中的 validate 不接受 `after`，只观察当前会话且不改变状态。两种模式都不得把临时建连后的 halted 状态表述为建连前事实。

Flash 边界不得硬编码为当前 S32K144 地址。Worker 先通过冻结 DLL 的 `JLINKARM_DEVICE_GetIndex/GetInfo` 读取器件数据库 Flash 区域，镜像段和范围擦除请求必须在首个目标副作用前完整通过 `jlink-domain` 的统一半开区间校验；器件不存在、区域为空或跨区时停止，不从 IAR 文件名、芯片常识或测试地址兜底。整片擦除使用 `JLINK_EraseChip`；范围擦除使用同一器件算法的 `BeginDownload → WriteMem(0xFF) → EndDownload` read-modify-write 路线，只允许在 3.7 真机证明请求区间擦除、相邻字节保留和目标最终状态后形成硬件能力证据，失败时不得改用普通 RAM 写入或 Commander fallback。下载前及默认校验前的 `reset_halt` 都是 Flash 算法和读回的内部准备动作，不属于成功后的 `after` 处理；因此 `after: none` 只表示成功修改及校验后不再执行额外状态转换，不能解释为整个请求都不改变目标状态。只有完整写入、所请求的校验和显式 `after` 全部成功才返回空成功；进入 Flash 修改调用后的失败路径不再执行 `after` 或隐式 reset/run。Flash 修改只使固件/验证缓存失效，不丢失持续到 disconnect 的活动目标配置身份，因此同一连接仍可执行后续独立 verify 或再次烧录。

### 6. 符号解析生成不可变访问计划

`jlink-mcp` 在设备操作前加载 ELF/DWARF，通过 `jlink-domain` 生成包含 ELF 身份、静态地址、大小、类型、成员偏移、位域和数组布局的 `AccessPlan`。Worker 验证计划指纹和当前目标固件身份后执行，不自行重新解释变量名。

结构体、数组、union、位域与柔性数组切片因此在普通读写和 HSS 中共享一套规则。柔性或动态长度数组必须独立提供 `slice {start,count}`；路径中的 `[i]` 不替代 `slice`，单元素也使用 `count:1`。3.2 只验证有效显式切片的计划生成机制，缺失或无效切片的 `SLICE_REQUIRED` 契约由 3.3 的 ART-004 主要测试覆盖。动态 location、逐样本指针跟随和无法固定的表达式在计划生成阶段拒绝。

`jlink-mcp` 按 ELF 内容 SHA-256、规范化选择器和解析器格式版本缓存 DWARF 索引与 `AccessPlan`。ELF 内容或解析器格式变化时缓存失效；目标固件身份变化时计划不得直接执行，必须先重新完成身份验证。缓存只保存不可变解析产物，不保存目标内存值或 Worker 会话状态。

烧录和独立校验优先使用自带装载地址的 ELF/AXF/OUT、Intel HEX 或 S-record。裸 BIN 不包含地址，因此 `jlink_program.flash/verify` 只对 BIN 要求每次显式提供十六进制 `base_address`；该值来自生成该 BIN 时选择的导出起始地址，不从芯片、文件名、默认镜像或相邻 OUT 猜测。字段对非 BIN 无意义并被拒绝。目标固件身份在同一连接会话首次变量或 HSS 符号操作前通过只读 Flash 段验证，成功结果只按 SES-005 的失效边界缓存。

访问计划可以把相邻且语义安全的普通 RAM 或静态变量区间合并为一次底层读取，再按原始字段边界在 Rust 中解码。MMIO、`volatile`、读取可能产生副作用的区域、跨访问区边界以及不满足目标对齐要求的区间不得自动合并。写入仍遵守完整预校验和既定原子性边界，不以合并为由扩大写入范围。

普通内存访问的 Flash/RAM 分类同样来自 `JLINKARM_DEVICE_GetIndex/GetInfo`；不在已知 Flash/RAM 区域内、也不跨越其边界的显式 Cortex-M 地址作为 MMIO 候选交给唯一 gateway，不能从芯片常识硬编码白名单。原始请求先完成 32 位地址空间、1–4096 字节和已知区域边界校验；目标特定的实际可访问性与传输对齐由冻结 J-Link 通用内存调用确认。读取必须返回精确字节数，写入必须返回精确写入数；对齐/能力失败、负返回或短写均不得重试或降级，可能已经发生部分副作用的写入统一返回 `EXECUTION_UNCERTAIN`。普通写入命中已知 Flash 时在首次 DLL 写入前返回 `ADDRESS_OUT_OF_RANGE` 并指向 `jlink_program`。

变量请求携带同一符号 ELF 生成的 `AccessPlan` 与固件身份计划。Worker 在每个连接会话首次变量操作前只读验证目标 Flash，成功后按 SES-005 缓存；变量读取只返回无损 `value`，变量写入先在当前字节副本上完成全部类型和值校验，再执行一次完整写入。`verify` 默认 `none`，不产生写后读回；显式 `readback` 才读取最终字节并只报告首个差异。活动 HSS 期间普通读取被拒绝；变量或 RAM/MMIO 写入只有在不需要新增固件身份读取且满足既定串行交错边界时才可继续。

V1 核心寄存器使用精确规范名称 `R0`–`R12`、`SP`、`LR`、`PC`、`XPSR`、`MSP`、`PSP`、`APSR`、`EPSR`、`IPSR`、`PRIMASK`、`BASEPRI`、`FAULTMASK`、`CONTROL`，不接受大小写折叠、`R13/R14/R15` 别名或模糊匹配。Worker 将该集合与活动目标经 `JLINKARM_GetRegisterList/GetRegisterName` 报告的目录取交集；`SP/LR/PC` 分别映射冻结 DLL 的 `R13 (SP)`、`R14`、`R15 (PC)`。DLL 目录中的 FPU、TrustZone 或其他架构扩展不因被列出而自动进入 V1。读取使用带逐项状态的 `JLINKARM_ReadRegs`；目录缺失或读取状态不支持时返回 `REGISTER_NOT_FOUND`。`XPSR`、`EPSR`、`IPSR` 作为只读视图在 `JLINKARM_WriteReg` 前拒绝并报告规范名称，其余已确认集合允许 32 位写入；非零写入状态不得表示为成功。

公共 `halt/resume/reset/step` 复用唯一 gateway 和会话状态。`reset` 只收口到请求的 `run` 或 `halt`；`step` 在调用 `JLINKARM_Step` 前观察当前状态，非 halted 时返回 `TARGET_STATE_INVALID` 且不得隐式 halt，成功后再次确认仍为 halted。控制后的实际状态写回会话；活动 HSS 对所有寄存器访问和公共控制在首次目标动作前返回 `OPERATION_CONFLICT`。

### 7. Capture Store 采用活动可恢复、完成不可变的模型

Worker 在调用 DLL Start 前完成最坏情况大小和所在卷可用空间预检，并以追加方式写活动 `.partial` 文件。自描述版本头保存采集身份、完整 `TargetConnectionSpec`、请求指纹和完整启动计划；每个 `BLK1` 块保存 payload 长度、CRC32、主机微秒时间和 live/tail 阶段，按固定字节间隔提交已校验边界。Stop 与尾排空结束后，Worker 先写入包含终态状态、块计数、payload 字节数和原始 SHA-256 的终态清单，同步并在临时文件上完成全量校验，再在同目录原子重命名为不可变 `.capture` 资源。MCP 只查询已提交边界；启动扫描将含有效终态的临时文件发布，将其余残留明确标为 `aborted + unknown` 并保留已验证块，未验证尾部不作为有效样本，完成资源不被扫描或自动删除。新 Worker 对完成和可解释的部分文件重建同键索引，持久化身份与当前探针、目标或规范化请求不一致时拒绝恢复，不覆盖或重写证据。

资源必须自描述并带版本，公共 MIME 固定为 `application/vnd.jlink-mcp.capture.v1+binary`。具体内部块编码和压缩方式在 Phase 0 吞吐实验后冻结；该选择不得改变 V1 查询语义，也不得静默丢弃重复样本。单次采集使用工程配置的 `capture.max_bytes`，默认 512 MiB、允许工程配置调低或调高；启动前同时检查估算大小和可用磁盘，运行时继续监控实际空间。

### 8. Phase 0 是生产实现前的强制门禁

Phase 0 只建立最薄的实验代码和证据，不搭建完整产品。为减少重复工作，将七项风险合并为四个实验包：

| 实验包 | 必须验证 | 通过证据 |
|---|---|---|
| F0-A HSS/写入/吞吐 | 以 6.98a 已成立场景为主线，验证 `GetCaps/Start/Read/Stop` ABI、结构体与标志位、帧、源时间单位/分辨率及到 `timestamp_us` 的无损归一化、持续与尾部排空、溢出/短帧/异常帧、串行写入调度影响以及 300 秒上界存储吞吐；8.38 和 9.70 仅作为兼容性副线 | 候选 DLL 版本与 SHA-256、探针/目标/固件身份、主副线说明、原始记录、解析断言、写入时间线、吞吐和空间结果 |
| F0-B Worker 生存与租约 | 父进程退出后续行、命名管道重新附着、同探针互斥、`capture_key` 幂等、临时文件恢复 | 可重复的进程测试日志、租约状态、同一采集 ID 和最终文件校验 |
| F0-C DWARF 复合类型 | 结构体、嵌套/多维数组、位域、union、柔性数组切片、64 位及非有限值的固定访问计划 | 代表性编译器 fixture、路径到偏移对照和编码往返断言 |
| F0-D MCP 客户端 | 六工具发现、严格 Schema、`structuredContent`、资源链接、工具错误、分页游标和长任务恢复 | Windows Codex 的准确应用包/CLI 版本、交互记录及能力矩阵 |

每个实验包只能得到 `PASS`、`PASS_WITH_LIMIT` 或 `FAIL`。四包都达到可接受结果才可进入生产纵向实现：`PASS` 直接接受；`PASS_WITH_LIMIT` 只有在限制不改变已确认公共能力、已写入实现约束且完成审查时才视为有条件通过。若限制影响工具、范围、HSS 时长/频率/变量、数据完整性、恢复保证或公共资源格式，必须先修改 OpenSpec 并由用户重新确认；`FAIL` 阻止生产实现。

F0-A 真机证据选择 J-Link 6.98a 作为 HSS 主线，使用其毫秒源时间戳模式；公共时间字段仍为整数微秒，通过 `milliseconds × 1000` 精确归一化，并显式保存 1 ms 源分辨率及跨时钟域误差。J-Link 8.38 和 9.70 作为兼容性副线，不以其微秒模式或长时 HSS 结果阻塞主线；三个 DLL 都按版本和 SHA-256 独立冻结。

### 9. 采用五阶段纵向增长

1. **P0 可行性**：完成四个 Phase 0 实验包和门禁裁决。
2. **P1 骨架与连接**：workspace、配置、MCP 六工具 Schema、Worker/IPC/租约、连接/状态/验证。
3. **P2 静态调试**：固件格式、ELF/DWARF、烧录/擦除/校验、变量/内存/寄存器和目标控制。
4. **P3 HSS 采集**：固定时长采集、写入交错、质量、自动停止、尾排空、恢复和存储。
5. **P4 查询与发布**：四种查询、阈值、分页、资源、客户端验证和最终支持矩阵。

每一阶段只增加可用的纵向能力，不提前实现后续阶段的公共功能。阶段结束运行受影响测试和一个最短 smoke；完整硬件/客户端回归只在 P4 发布门禁运行一次。

交付分支以完整 V1 为边界，而不是按 P1、P2、P3、P4 分别建立待合入 `main` 的功能分支。P0 在独立可行性分支冻结实验、设计和门禁证据；后续单一 V1 实现分支按 P1→P4 顺序开发，在各阶段形成可验证提交和检查点，但不提前合入 `main`。只有完成任务 5.7、通过全量发布门禁并完成分支复核后，才为整个 V1 基本功能向 `main` 提交一个 PR。P0 实验代码只作为行为、约束和测试路线参考，不直接演化为生产架构。

### 10. 验收以 Requirement→主要测试→证据追踪

每条 Requirement 指定一个主要测试用例；一个端到端用例可以覆盖多条 Requirement，但不得为同一行为在 unit、integration、hardware 三层机械复制相同断言。

任务开发和局部修复只运行当前任务的主要测试、最短复现和直接受影响回归，不在阶段中途重复 workspace 全量门禁或已通过且输入指纹未失效的硬件证据。原子提交前固定执行格式检查、受影响 crate 及必要直接下游的 `clippy -D warnings`、当前主要测试/直接回归和 `git diff --check`；仅在对应输入发生变化时执行 OpenSpec strict、依赖方向或 LikeC4 校验。公共 MCP Schema、IPC 合同、核心状态机、Capture Store 格式、硬件 ABI、恢复逻辑或安全边界变化时必须扩展到相关下游和合同测试，不得省略 Requirement 的唯一主要测试或用 Mock 替代真机证据。完整 workspace 格式、Clippy、测试、依赖、OpenSpec、diff 和阶段纵向 smoke 仅在 4.8、5.5 各执行一次，5.7 发布门禁不提前执行。测试、环境和硬件证据在相关代码、输入、身份、配置、Schema 与验证合同指纹未变化时持续有效；仅补录说明、状态或证据索引不得触发重复验证。

- 纯边界、状态转换、编码和查询算法优先用快速单元/fixture 测试。
- 进程、IPC、原子文件和恢复只用必要的本机集成测试。
- DLL、探针、目标时间行为和客户端兼容声明只由硬件或目标客户端验收。
- 每份证据记录测试版本、实现二进制、DLL/探针固件、目标/固件/ELF、OS、客户端和关键配置指纹。
- 昂贵的硬件或客户端证据在相关指纹与 Requirement 未变化时 MUST 复用；任一相关指纹或行为规格变化时才失效并重测。

验收矩阵是 change 的门禁组成部分，不另建脱离 Requirement 的重复测试项目。任务清单只引用 Requirement ID、主要测试 ID 和证据类型，不重复抄写完整 Scenario。

### 11. 性能观测保留在本地诊断边界

实现必须在本地结构化日志中区分配置与 DLL 验证、探针连接、ELF/DWARF 解析、`AccessPlan` 缓存命中、单次 DLL 调用、HSS 排空、交错写入等待、数据解析和资源落盘耗时。该观测用于定位瓶颈和形成 Phase 0/发布证据，不得默认附加到普通 MCP 成功结果；Agent 只有在显式诊断时才获取必要摘要。

## Risks / Trade-offs

- **HSS ABI 来源不完整**：旧版行为和社区镜像可能与候选 DLL 不一致。通过导出检查、版本/哈希冻结、最小 FFI 和 F0-A 原始证据限制风险；未证明的结构不得进入生产绑定。
- **V2 串行调度影响采样**：旧版已证明长时采集和控制写入可以共存，但 V2 的最小 FFI、调度器和候选 DLL 仍可能扩大排空间隔。V1 记录写入区间和质量影响；F0-A 用于量化并约束 V2 实现，而不是重新判断该业务场景是否成立，也不因此引入无证据的 DLL 并发。
- **Worker 续行增加进程复杂度**：换取固定时长采集不依赖 Agent 存活。以命名管道、探针租约、采集键和有限续行范围控制复杂度。
- **四个 crate 仍有共享类型耦合**：共享只允许不可变值对象和纯规则；设备状态不进入共享全局变量。发现循环依赖时应移动规则到下层，而不是增加回调或全局容器。
- **自描述原始资源占用空间**：完整性优先于默认压缩上下文。512 MiB 硬限制、预估和可选块压缩控制磁盘风险，Agent 通过查询视图而非内联资源消费数据。
- **目标固件身份验证成本**：首次验证可能较慢。连接会话内缓存并按明确事件失效，避免每次调用重复验证。

## Migration Plan

V2 不迁移旧版运行状态、配置或采集文件。实施顺序为：完成并冻结 Phase 0 证据；建立新 Rust workspace；逐阶段实现；生成仅含占位符的可共享配置示例；完成 P4 验收后再发布首个版本。若某个 Phase 0 门禁推翻公共能力，先修订本 change，不保留兼容垫片。

回退方式是停止当前阶段并保留上一阶段可验证产物；在首版发布前不存在需要兼容的生产数据。任何实验性 DLL 绑定和采集格式在门禁冻结前不得被声明为稳定接口。

## Open Questions

- F0-A 主目标已确定为已连接的 S32K144 板、SWD、4000 kHz 和实际 IAR 工程固件；探针型号/序列号及最终固件指纹在实验开始时自动登记为证据身份。
- F0-C 主编译器已确定为 IAR 8.32；隔离测试 fixture、实际构建配置和产物指纹在创建 fixture 时登记，只有实际通过的组合进入支持矩阵。
- Capture Store 的内部块编码和压缩由 F0-A 吞吐与恢复结果冻结；公共 MIME 已固定，查询语义和完整数据要求不随内部选择改变。
- J-Link 6.98a 主线及 8.38/9.70 副线的最终支持等级，必须由各自文件版本、SHA-256 和真机结果决定；不得把副线结果外推为主线能力。
