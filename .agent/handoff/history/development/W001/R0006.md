# W001 J-Link MCP V2 首版实现交接

> P0 已以提交 282091c 冻结并推送到 origin/codex/p0-feasibility，未合入或修改 main。后续单一 V1 实现分支将按 P1→P4 完成全部基本功能与完整验证，仅在任务 5.7 发布门禁通过后向 main 提 PR。

## 目标

在 Windows x64 上实现内部个人使用的 Rust J-Link MCP V2：通过本机 stdio 为 Windows Codex 提供烧录、校验、ELF/DWARF 变量与原始内存读写、核心寄存器、目标控制，以及固定 1-300 秒 HSS 采集和确定性查询；最终以真机和目标客户端证据完成验收。

## 当前状态

P001 仍为 in-progress。P0 总裁决为 PASS_WITH_LIMIT，OpenSpec 任务 1.1-1.6 已完成。P0 设计、OpenSpec、实验源码和 Markdown 验证报告已在 codex/p0-feasibility 提交为 282091c8a285e12be50e73a47183251894b80a88，并推送到 origin/codex/p0-feasibility；本地 main 保持 c621728，未执行合并。后续 V1 实现分支尚未创建。Windows Codex 的隔离 P0 mock jlink_p0_v2_probe 仍与旧 jlink server 分离。

## 已完成工作

F0-A 使用 J-Link 6.98a、S32K144、SWD 4000 kHz 完成 10 blocks × 1 kHz × 300 秒采集、300004 samples 和 3 次交错写入。F0-B 验证 Windows named pipe 重新附着、父进程退出续行、capture_key 幂等、租约和 partial 恢复。F0-C 使用 IAR 8.32.3 完成 DWARF 3/4 和 15/15 AccessPlan。F0-D 通过 SDK 自测及四次隔离 Windows Codex 运行验证六工具、closed Schema、structuredContent、resource_link、结构化错误、分页和新进程恢复。architecture、openspec、experiments/p0 和 validation Markdown 已首次纳入版本控制；构建产物、node_modules、安装包和 validation/evidence 继续忽略。

## 决策与约束

用户确认 J-Link 6.98a 为主线，8.38/9.70 为兼容性副线；不需要微秒模式，普通 J-Link 的 HSS 上限按 1 kHz 处理。主目标为 S32K144、SWD 4000 kHz、IAR 8.32.3 和实际 SVN 工程。V1 唯一目标客户端为 Windows Codex。P0 mock 只能使用 jlink_p0_v2_probe，不能作为生产版本或与旧 jlink 混用。交付分支以完整 V1 为边界：P0 分支仅冻结可行性；后续一个 V1 实现分支顺序完成 P1、P2、P3、P4，在阶段内形成提交和检查点，但不按阶段分别合入 main；任务 5.7 全量发布门禁通过后才向 main 提交一个完整 PR。P0 实验代码仅作行为、约束和测试路线参考，不直接演化为生产架构。SVN 既有受控修改不得覆盖。

## 失败尝试

J-Link 8.38/9.70 对当前探针弹出 clone warning，未作为主线，且该现象不作为探针真伪的最终裁决。早期把目标客户端误判为 ChatGPT Desktop 并规划 Secure MCP Tunnel，该路径已由用户纠正。首次用全局 Codex 配置运行客户端测试被无关的 markitdown MCP 配置错误阻止，随后通过 --ignore-user-config 且只注入 jlink_p0_v2_probe 完成隔离验证。

## 风险与未知

F0-A 时间戳分辨率为 1 ms 且无独立 overflow/sequence counter；生产实现必须保留真实质量证据。F0-B 文件租约在强制终止时可能遗留，生产实现需 kernel lease 或 PID validation。Windows Codex 在 approval_policy=never 下会阻止 destructiveHint 工具，需要正常审批流程。P0 原始 evidence 仍为本机忽略内容，远端提交保存的是可复现实验源码、冻结身份摘要和报告，不包含大体积原始记录。
