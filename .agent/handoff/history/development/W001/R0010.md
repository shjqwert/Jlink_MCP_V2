# W001 J-Link MCP V2 首版实现交接

> codex/v1-implementation 已提交 P1 2.1-2.4，2.5 实现仍未提交。冻结 J-Link 6.98a 上，同一 Worker/DLL 会话真实 HardFault 注入与生产 reset/run 恢复已通过；完整 T-P1-SES 随后因 disconnected validate 返回 Halted、测试期望 Running 而暂停，需用户裁决 validate 的副作用与最终状态合同。

## 目标

在 Windows x64 上按已确认 OpenSpec 和受控无人开发规则完成 J-Link MCP V2 的 2.1-5.5；当前完成 P1 2.5 单活动目标、验证缓存和 halted/HardFault 恢复，5.6/5.7 与 JTAG 真机验证保持待办。

## 当前状态

分支 codex/v1-implementation 相对 origin/codex/v1-implementation ahead 4。2.1-2.4 已分别提交；2.5 的 domain、IPC、Worker gateway、会话状态机、MCP WorkerClient、测试脚本和 OpenSpec 修订均在工作树中未提交。冻结 DLL/OUT/探针/目标指纹一致，无残留 JLink 或 jlink-worker 进程。完整 T-P1-SES 在真实 HardFault 恢复通过后，于 disconnected validate 场景失败并依约停止。

## 已完成工作

已实现并通过纯测试的 TargetConnectionSpec、连接/状态/断开/显式验证、验证缓存失效、恢复诊断及 IPC 路由。halted 真机路径返回 ResumedFromHalt。通过冻结 DLL 导出表和机器码确认 JLINKARM_WriteReg 的两个 32-bit 参数与字节返回 ABI，仅在 cfg(test) 下绑定；直接写 PC 后，同一 gateway 会话真实观察到 HardFault，生产 recover_target 完成 reset/run，真机用例通过。

## Bug 诊断

本次新失败不是 HardFault 恢复失败。TargetSessionManager::validate 在断开状态下调用 gateway.open_target；S32K144 的 J-Link 初始化将目标置为 Halted。实现随后只生成 ValidationReport 并 close_target，不调用 recover_target，因此报告 target_state=Halted。领域文档又明确 ValidationReport 是“without automatic recovery”，而硬件测试要求 Running；测试期望、实现注释和 SES-006“无业务副作用”之间存在设计语义冲突。

## 决策与约束

代码定位、实现、调试与修复仅由主窗口执行；不使用子代理写代码。当前硬件证据只允许 S32K144、SWD 4000 kHz、J-Link 6.98a。真实 HardFault 注入仅测试编译可见，不进入生产 IPC/MCP，不修改 Flash/OUT。发现设计问题必须停下请用户确认；不得通过放宽断言、Mock、重试或隐藏状态绕过。所有阶段提交使用中文固定模板，2.7/3.7/4.8/5.5 才集中推送。

## 失败尝试

连接前由 Commander 注入的 HardFault 会被器件专用 J-Link 初始化归一化，不能证明 Worker 观察到真实故障。随后通过 JLINKARM_WriteU32 写 DCRDR/DCRSR 的间接 PC 路径未改变 PC，回读仍为 0x00029E9C；该路径已停止。改用只读机器码确认后的测试专用 JLINKARM_WriteReg，真实 HardFault 和恢复成功。完整脚本最终因 detached validate 返回 Halted 而失败，未再次修改或重跑。

## 验证

已观察 cargo fmt、严格 Clippy、T-P1-SES domain 3/3、Worker 纯会话 4/4 通过。真机 halted 恢复通过；hardware_hardfault_recovery_uses_same_gateway_session 通过。随后 validate 的 7 个检查全部 passed、target_id=0x2BA01477、validation_runs=1，但 target_state=Halted 导致完整脚本失败。清理脚本执行 VCatch 0 和 go。DLL SHA-256 D15D5A24DC86F135C0B1FAFEB89F0E577691B6A85F3A19C773B3E20D0B95BBE5，OUT SHA-256 3EB79013870DBB6F9B6ADC929C3B43D8D30C4FF35D69A4D2D39A78643526EFEF；受保护文件哈希未变。

## 剩余工作

先由用户裁决 disconnected validate 的目标终态合同：是否允许它复用 SES-003 自动恢复并最终保持 Running，还是必须维持纯观察并调整可用场景/Schema。确认后先同步 OpenSpec、领域模型和主测试，再做一次最小根因修复与受控真机复验；全部通过后更新 requirement matrix、勾选 2.5、运行阶段所需门禁并提交 [P1-2.5][开发]，然后继续 2.6。

## 风险与未知

无法从连接后的 Halted 状态可靠推断连接前目标是 Running 还是用户主动 Halted；因此 detached validate 若自动 resume 可能改变用户原意，若不恢复又可能把原本 Running 的目标留在 Halted。该取舍必须成为显式合同，不能只修测试。当前 2.5 工作树未提交，不得误认为任务完成。

## 证据

冻结 DLL 的 PE 导出 JLINKARM_WriteReg 位于 RVA 0x000D67B0；对应机器码读取 ECX/EDX 两个 32-bit 参数并以 movzx eax, bl 返回。官方 SEGGER J-Link SDK 页面说明权威声明位于未安装的 JLinkARMDLL.h/UM08002。硬件日志显示 HardFault 真机用例 ok，随后 ValidationReport 的七项检查全部通过但 target_state=Halted。
